01Processes and mailboxes

Look for: a receive that can take a message meant for another request (no ref, or a ref left unpinned); a receive with no way out when the other process dies; a loop that leaves unknown messages in its mailbox; and self() called inside the function a new process runs.

Why it bites: a late reply answers the next request, so one customer sees another's price. A mailbox nothing drains grows until the node runs out of memory. A worker that crashes before it replies leaves its caller waiting forever. Spawning and then monitoring races: a worker that dies first leaves only :noproc, so spawn_monitor sets the monitor as it spawns.

Review habit: Name the other process. For each send, say who receives it and what happens if that process is dead, slow or never answers. For each receive, say who sends what it matches, and what else could be in the mailbox when it runs. Messages from one process arrive in the order it sent them; that is the only ordering the runtime promises, so a result sent just before its sender exits always arrives before the :DOWN.

A common mistake: flushing the mailbox, or adding after, instead of tagging the request. A flush throws away messages meant for other code and misses a reply still on its way; a timeout turns a crash into :timeout and loses the reason. Put a make_ref() in the request and pin it in the receive. With a hand-made ref, the late reply still sits in the mailbox, so a long-lived caller must drop it later or not care. OTP's GenServer.call tags its requests too (chapter 3).

02Links, monitors and exits

Look for: spawn_link or Task.async where the caller must outlive the work; a process that traps exits but has no clause for {:EXIT, pid, :normal}; a monitor still held once the answer came; and Process.exit(pid, :normal) used to stop a process.

Why it bites: one bad email address takes the notifier down, and every in-flight notification goes with it. A long-lived client that never removes its monitors holds one more for every request, and each server that dies leaves a :DOWN that nothing reads.

Review habit: Ask what happens on crash. For each process a line starts or watches, say what reaches the other side when it ends, normally or not. The runtime's rules: a link carries an exit signal both ways, and a process that does not trap exits dies of any reason except :normal. Trapping turns the signal into an {:EXIT, pid, reason} message, :normal included. Process.exit(pid, :kill) cannot be trapped, and links and monitors see the reason :killed. A monitor is one-way and delivers one :DOWN message. Linking a Task.async to its caller is Elixir's choice; Task.Supervisor.async_nolink monitors the task without the link.

A common mistake: wrapping spawn_link in try/rescue. The crash happens in the other process and arrives as a signal, so no rescue in the caller sees it, and trapping exits in the caller only turns it into mail the caller must read. Start the process unlinked, or monitor it and read the :DOWN. Unlinking after the start (spawn_link then Process.unlink, or Task.async then Task.ignore) leaves a window in which a fast crash still takes the caller. Once the answer is in, Process.demonitor(ref, [:flush]) removes the monitor and any :DOWN already waiting.

03GenServer calls and timeouts

Look for: a decision made in the caller on a value an earlier call returned; slow work inside a callback; replies deferred with {:noreply, ...} that are lost or kept after use; from used as a key; a Process.monitor with no :DOWN clause; and a server that calls itself, or calls a server that calls it back.

Why it bites: two customers both read the last unit and both buy it. One slow refresh holds the server, so every caller queues behind it until its call times out. A registry that monitors clients but never handles :DOWN grows with every client that ends.

Review habit: Ask what happens with two at once. A server runs one callback at a time, so a check and the act that depends on it are safe together only inside one callback; between two calls, another caller's request can run. For each callback, ask who else waits while it runs. A from kept for GenServer.reply/2 is answered once, then dropped. from holds the caller's pid and a tag that is new on every call; the tag's shape is OTP's internal, so key by the pid. A monitor delivers one :DOWN, and a clause has to handle it. {:continue, ...} returned from init runs before the server takes any message.

A common mistake: catching a call's timeout and treating the request as cancelled. The caller exits with {:timeout, ...}, but the server keeps working on it. Since OTP 24 a reply that arrives after GenServer.call gave up is dropped rather than left in the caller's mailbox: OTP's gen_server:call docs say so, Elixir's GenServer.call docs still describe the older behaviour, and it holds for calls, not hand-made requests (chapter 1). Move slow work into a Task that sends its result back to handle_info. OTP's gen_server:call refuses a call to the caller's own server: the caller exits with :calling_self. Two servers that call each other each wait for the other until one call times out, or for ever with :infinity.

04Supervision and restarts

Look for: a child listed before a sibling its init calls; a sibling's pid kept from init under a strategy that restarts the sibling alone; the default :permanent on work that runs once; an init that crashes when a call in it fails; and code that expects a restarted process to keep its state.

Why it bites: while the database is down the app will not boot, health check included. After a producer restarts, every event goes to a dead pid. A finished warm-up job is restarted until its supervisor gives up, which the one above restarts if :permanent.

Review habit: Read for what is missing: a restart: option, an {:error, _} branch, a sibling that has to start first. In a trace, start from the first app frame. OTP documents these rules. A supervisor starts its children in list order, one start returning before the next begins, and stops them in reverse. A restarted child starts again from init. :permanent restarts on any exit, :transient only on a reason other than :normal, :shutdown or {:shutdown, _}, and :temporary never. When a child is to be restarted, :one_for_one restarts only it, :rest_for_one also the children after it, and :one_for_all every child. After more than max_restarts restarts in max_seconds, the supervisor stops its children and exits with :shutdown; Elixir's Supervisor defaults to 3 in 5 seconds, Erlang's supervisor to 1 in 5. A crash in init fails the child's start, so the tree does not boot; a crash in handle_continue comes after the start returned.

A common mistake: :one_for_all so a consumer gets the restarted producer's pid; a consumer crash then restarts the producer too, and its state is lost. Put the producer first under :rest_for_one, or have the consumer look the producer up by name on each call. Raising max_restarts only lets a job that is restarted after every stop run more times, and catching the exit in a cache's init boots it empty.

05ETS

Look for: a lookup or member check followed by a separate write; a table written by processes other than its owner while it is :protected; a table created by whichever process calls first; a match spec's guard at a boundary; a select_delete body not true.

Why it bites: two workers both see a job as free, and both process it. A rate limiter raises ArgumentError on every request from its first deploy. Feature flags vanish when the request that happened to create their table ends.

Review habit: Ask what happens with two at once. OTP documents each update of a single object as atomic and isolated, but nothing holds between two calls: another process can write in the gap. insert_new writes only if the key is absent, and update_counter adds in place, so put the decision in the call that writes. A table belongs to the process that created it and is deleted when that process dies, unless it has an :heir; OTP's docs do not say whether that happens before or after the owner's :DOWN. :protected, the default, lets any process read and only the owner write; :public lets any process write; :private keeps both to the owner. read_concurrency and write_concurrency are performance tuning: they change neither access nor atomicity. A :set keeps one object per key, a :bag each distinct object, a :duplicate_bag every copy, and an :ordered_set walks its keys in term order. select_delete deletes only the rows for which the match spec returns true.

A common mistake: acting on a lookup or member check in front of the write. Two callers both pass it before either writes. Let the write decide alone: insert_new and its result, update_counter with a default row, or one call in which the owner checks and writes. The course asks for one atomic insert_new and no read before it, as its own choice: a member check ahead of an insert_new you honour is no race, only redundant. Create a shared table in the init of a supervised process, never on first use.

06Ecto queries and transactions

Look for: a get! or query that takes an id but not the signed-in user; a cast that permits user_id; SQL built by interpolating a string; a notification sent inside Repo.transact; Repo.preload called once per row; and a count written back from a struct loaded earlier.

Why it bites: anyone who edits the id in a URL reads someone else's post. A "welcome" email goes out for a signup that rolled back. A profile page runs 501 queries. Two tabs count one view.

Review habit: Ask who supplied the value. Ids, form params and search text come from the client. Scope the query by the session's user, so "not yours" raises the same Ecto.NoResultsError as "not there" (get!, get_by! and one! raise it; get and one return nil), and cast only the fields a user may set. Pass values as parameters: Ecto sends each ^ value apart from the SQL text, Repo.query!/2 takes ? on SQLite and $1 on Postgres, and Ecto rejects an interpolated string as fragment's SQL at compile time. Repo.transact/2, Ecto's choice since 3.13, commits on {:ok, _} and rolls back on {:error, _}; the soft-deprecated transaction/2 commits whatever the function returns. A Multi checks the changesets it was given before the transaction starts. update_all and insert_all take no changeset and fill no timestamps, so a NOT NULL timestamp fails with the driver's error (Exqlite.Error here, Postgrex.Error on Postgres); update_all with inc: is one UPDATE. A unique index raises Ecto.ConstraintError unless the changeset declares unique_constraint/3 under the index's name: Postgres reports that name, while ecto_sqlite3 builds it from the table and columns SQLite reports.

A common mistake: notifying as the transaction's last step. The commit can still fail, so notify once Repo.transact has returned {:ok, _}. And a preload through an inner join: drops posts that have no comments; left_join: keeps them.

07LiveView

Look for: a handle_event that acts on an id without asking whose it is; a phx-value-* compared with an integer; String.to_atom on anything a client sent; one PubSub topic for every user's private items; and URL state read in mount but not in handle_params.

Why it bites: a client can send any event with any value, as render_click/3 does here, so hiding a button guards nothing. Someone deletes another user's note; a pick never shows, because "2" == 2 is false; the node stops when its atom table fills, since atoms are never garbage collected; a private item appears in someone else's feed.

Review habit: Ask who supplied the value. Params, phx-value-* values and the URL come from the client; a phx-value-* attribute is text, so it arrives as a string. LiveView documents that mount/3 runs twice, for the plain HTTP render and again once the socket connects (connected?/1 tells them apart), that a routed view's handle_params/3 runs after mount and on every patch, and that push_patch keeps the process, push_navigate mounts a new one and redirect reloads the page. So authorise in the handler against the session's user, and answer "not yours" as you answer "not there"; map column names through an allow-list; read URL state in handle_params; broadcast private data on a per-user topic, since PubSub delivers every message on a topic to each subscriber. A forged or malformed value may stop the forger's own view, so this course accepts String.to_integer, String.to_existing_atom and guards with no fallback clause; it asks that no other user's data is shown or changed and no atom is made. A LiveView with no handle_info/2 logs a stray message at debug level and carries on: that is LiveView's choice. A handle_info with no catch-all crashes on it.

A common mistake: dropping other users' items in handle_info. The checks pass, but each private item still reaches every subscriber's process.

08Quire

Look for: what each function leaves out. The code is shaped like Quire, the notes app from the phoenix-koans course: an id used without Id.cast, search text sent to FTS5 as typed, a page cursor with no tiebreak, an upsert's returned rows taken as every row, a broadcast that ignores the result, and a form save that checks no version.

Why it bites: Ecto.Type.cast(:id, _) accepts any integer, but SQLite integers are 64-bit, so a longer id from a URL raises in the driver. In an FTS5 query a " ends a phrase, and NOT or body: are syntax. Notes saved in the same second share an updated_at, so a cursor on it alone skips or repeats them; an offset shifts whenever a newer note is saved. With on_conflict: :nothing, returning gives back only the rows inserted. A second tab's save overwrites the first.

Review habit: Read for what is missing: the id's range; the owner, so every query is scoped by the session's user and "not yours" reads as "not there"; a tiebreak column; the rows the insert skipped; the {:error, _} branch; the version the form was rendered with. Scope PubSub topics by user as well, since each subscriber gets every message on its topic. ecto_sqlite3 stores utc_datetime as ISO-8601 text, which is the adapter's choice, so < compares strings, and the fixed width keeps that in time order. Inside FTS5 quotes, "" is one quote; dropping quotes works too, as the default tokenizer ignores them. optimistic_lock/3 plus stale_error_field: turns a stale save into {:error, changeset}; without that option, Repo.update raises Ecto.StaleEntryError.

A common mistake: a row-value cursor, fragment("(?, ?) < (?, ?)", ...), with the timestamp pinned untyped. exqlite then sends it without its Z, so it never equals the stored text; write type(^updated_at, :utc_datetime).

01Shared mutable state

Look for: a mutable default argument (=[], ={}, =set()); a lambda or nested def in a loop that reads the loop variable; [[...]] * n; dict(...), copy.copy or {**...} on nested data that is then written to; a mutable class attribute used as per-instance state.

Why it bites: the language evaluates a default once, when def runs, and a class body once, when class runs; every call or instance after that shares the one object. A closure looks its variables up when it runs, not when it is made. So one request's errors, or one user's token, shows up in the next request, and nothing fails until two calls happen in one process.

Review habit: Ask what happens with two at once. Call the function twice, or make two objects, and follow every mutable value back to where it was created. If it was created once, at definition time or at module level, each write lands where the next caller will read it.

A common mistake: patching the symptom. errors = errors or [] drops the caller's empty list; copying an argument the caller shares on purpose breaks callers that rely on it; a shallow copy of nested data still shares the inner dict. self.items = self.items + [sku] happens to work but leaves the shared list in place for the next method that appends, and self.items += [sku] is not that rebind: += extends the shared list in place. Give each instance its own list in __init__. A traceback can miss the cause: in the 01_note trace, the field at fault is on line 7, which no frame prints. Read the error, then find the field it names.

02Equality, hashing and iteration

Look for: is between values; a one-item tuple written without its comma; NaN in a comparison or a lookup; a dataclass with eq=False, or a hash over fields that can still change; a generator or iterator read twice; a dict or list changed inside a loop over it; zip over inputs that may differ in length.

Why it bites: most of these raise nothing. A parenthesised string like ("x") is still a string, so in matches any part of it. A generator is empty after one full pass, so a second sum over it is 0. zip stops at the shorter input. With eq=False, equal records compare and hash by identity, so a set keeps both. NaN is not equal to itself, but in tries is before == (the language's rule), so the same NaN object is found and a fresh one is not. A list loop walks by index, so removing an item shifts the next one under the index and it is skipped. A dict is the exception: changing its size inside the loop raises RuntimeError at the for.

Review habit: Ask who supplied the value. is compares identity, which is the language's rule; whether a string parsed from JSON is the same object as the literal in your source is CPython's behaviour, and here it is not. A parameter typed Iterable may be a reader that runs once. A header row and a data row come from different places and can disagree in length.

A common mistake: fixing what the eye lands on. rows = list(rows) copies the input but still reads one generator twice, and filter(...) is one pass too. unsafe_hash=True dedupes equal records but loses one edited after it went into a set. A length check in one direction catches half the bad rows. A traceback can name the wrong line: the 02_drop_expired trace points at the for on line 2, but the del on line 4 changed the dict.

03Exceptions

Look for: except Exception around code that can fail for more than one reason; a from None inside a handler; a broad handler above a narrower one; continue or pass as the whole handler; a handler that raises again; a name bound by except ... as and read after the block.

Why it bites: the program keeps going with the wrong answer. A port of 80a becomes 8080, and a failed push drops out of the report. The language tries except clauses top to bottom, so for an Exception subclass a handler below except Exception never runs. from None hides the context in the traceback without deleting it, and __cause__ stays None, so a caller that reads the cause gets nothing. The language also deletes the as name when its handler ends, even a name bound before try.

Review habit: Read for what is missing. For each handler, ask which exceptions it catches that its author did not mean, and what record of the failure is left once it has run: a status, an entry in a list, a __cause__. An empty handler, or a from None, is a choice to lose one. Which OSError deleting a directory gives is the platform's: macOS and Linux differ.

A common mistake: narrowing in one place only. except (KeyError, ValueError) still turns a bad port into 8080; moving only ValueError up still sends NotFound to 500; append then break reports the first failure only; dropping from None shows the context again, but __cause__ is still None. Checking that a file exists before unlinking it races: another process can delete it in between, so the unlink still meets a missing file. A chained traceback prints two errors. In the 03_parse_order trace, the first is the request's fault (a missing value at column 22) and the last is the code's. In the 03_last_error trace, the handler on line 6 deleted the name the return reads.
